# @luna/sync — Notion → Postgres 동기화

사이트 서버(`apps/admin`)가 15분마다 자식 프로세스로 실행한다. Notion 4개 DB에서 **바뀐 페이지만** 읽어 Postgres에 반영하고, 사진은 WebP로 바꿔 Postgres `image_files`에 넣는다(사이트 빌드가 꺼내 `/img/` 정적 파일로 내보냄). 바뀐 게 있으면 `SYNC_NOTIFY_FILE`에 파일을 남겨 서버가 사이트를 다시 만들게 한다.

## 명령

```bash
pnpm sync                 # 증분 동기화 (루트 .env를 자동으로 읽음)
pnpm sync --dry-run       # DB 쓰기와 빌드 호출 없이 무엇이 바뀔지만 출력
pnpm sync --full          # 마지막 동기화 시각을 무시하고 전부 다시 반영
pnpm sync --check-schema  # Notion 스키마만 확인하고 끝냄
pnpm --filter @luna/sync test
```

`--dry-run`과 `--check-schema`는 `NOTION_TOKEN`과 `NOTION_DB_*`만 있으면 된다. `DATABASE_URL`이 없으면 첫 실행처럼 전부 새 항목으로 보고 확인한다. 실제 실행에는 `.env.example`의 Notion·DB·GitHub 값이 모두 필요하다.

따로 배포하는 서비스는 없다. 사이트 서버가 `pnpm --filter @luna/sync start`로 실행하며 서버의 환경 변수(Railway Variables)를 그대로 넘긴다. 로컬에서는 `pnpm sync`로 직접 돌릴 수 있다(이때는 빌드 알림 없음).

관리자 페이지의 "지금 다시 동기화"는 같은 명령을 GitHub Actions(`.github/workflows/sync.yml`, `SYNC_TRIGGER=admin`)에서 돌린다. 실행은 시작할 때 `sync_state._running`을 잡고, 다른 실행이 잡고 있으면 아무것도 하지 않고 종료 코드 0으로 끝난다(`--dry-run`은 잠그지 않음).

## 한 번의 실행 순서

1. **스키마 확인.** 4개 DB의 속성 이름(대소문자 포함)과 타입을 요청서 표와 비교한다. 하나라도 다르면 아무것도 쓰지 않고 차이를 출력한 뒤 종료 코드 2로 끝난다. 표에 없는 속성은 참고로만 출력한다.
2. **변경분 조회.** DB마다 `sync_state.last_synced_at - 5분` 이후 수정된 페이지만 `last_edited_time` 필터로 조회한다(첫 실행·`--full`은 전체). Notion의 수정 시각이 분 단위로 잘리고 검색 색인이 늦을 수 있어 5분을 겹쳐 읽고, DB에 저장된 수정 시각과 같으면 건너뛴다.
3. **변환·upsert.** 속성을 `@luna/db` 스키마로 바꿔 `notion_id` 기준 upsert. rich_text는 줄바꿈을 유지한 채 일반 텍스트로 합친다. FAQ `order`가 비어 있으면 맨 뒤(`2147483647`)로 보낸다.
4. **이미지.** 아래 "이미지" 절.
5. **삭제.** Notion에 살아 있는 페이지 ID 목록(제목 속성만 받아 가볍게)과 DB를 비교해, 사라졌거나 휴지통에 간 페이지를 지운다.
6. **사진 파일 정리.** 어느 테이블도 쓰지 않는 `image_files` 행을 찾아, 처음 발견하고 유예 시간(기본 120분)이 지나면 지운다. 배포된 사이트는 자기 사본을 갖고 있지만, 진행 중인 빌드가 방금 읽은 행의 사진을 꺼내기 전에 지우지 않기 위해서다.
7. **빌드 알림.** 추가·수정·삭제가 하나라도 있으면 `SYNC_NOTIFY_FILE`에 파일을 쓴다. 없으면 쓰지 않는다.
8. **기록.** DB별 결과(추가·수정·그대로·삭제·실패 개수, 올린 이미지 수, 소요 시간)와 오류를 로그와 `sync_state`에 남긴다.

## 속도 제한

Notion API 요청은 모두 **하나의 대기열**(p-queue, 1초에 3개)을 지난다. 429·529 응답이면 `Retry-After`만큼 **대기열 전체를 멈추고** 같은 요청을 다시 넣는다(한 요청만 쉬면 나머지가 계속 제한에 걸리므로). 500·502·503·504는 지수 대기로 다시 시도한다. 최대 8번까지. SDK 자체 재시도는 대기열을 거치지 않아 끈다(`retry: false`).

Notion-Version은 `2026-03-11`(공식 SDK `@notionhq/client` 5.x). 이 버전부터 데이터베이스 안의 data source를 조회하고, `archived` 대신 `in_trash`를 쓴다. `NOTION_DB_*`에는 데이터베이스 ID나 data source ID 어느 쪽을 넣어도 된다. 데이터베이스에 data source가 여러 개면 어느 것을 쓸지 몰라 멈추니 data source ID를 넣는다.

## 이미지

- Notion 파일 URL(1시간 뒤 만료)은 내려받는 데만 쓰고 **DB에도 HTML에도 저장하지 않는다.**
- 원본 바이트의 SHA-256으로 키를 만든다. DB `image_key`는 `members/<sha256>`(awards/, projects/ 동일), `image_files` 키는 `<image_key>-480.webp`, `-960.webp`, `-1600.webp` 세 개. 원본이 작으면 늘리지 않고 원본 폭으로 저장하지만 파일 이름 세 개는 항상 있다(사이트 `srcset`이 단순해진다).
- EXIF 회전을 반영하고 메타데이터(EXIF·GPS)는 지운다. 움직이는 GIF는 첫 프레임만 쓴다.
- `image_width`·`image_height`는 1600 이하로 줄인 최대본의 크기. 사이트가 `width`/`height`로 레이아웃 흔들림을 막는다.
- 1600 파일을 맨 마지막에 올리고, 이 파일이 있으면 세 개 모두 올라간 것으로 본다. 업로드가 중간에 끊기면 다음 실행에서 다시 올린다.
- 키가 내용 해시라 같은 키의 내용은 바뀌지 않는다. 사이트는 `/img/*`에 `Cache-Control: public, max-age=31536000, immutable`(`apps/web/public/_headers`)을 붙인다.

### 다운로드 최적화

| 방법                                                                    | 효과                                                                                                             |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Notion 파일 주소(서명 쿼리 제외)별 캐시 (`sync_state`의 `_image_cache`) | 글만 고친 페이지는 사진을 다시 내려받지 않는다. `image_files`에 파일이 실제로 있는지 확인한 뒤에만 캐시를 믿는다 |
| 같은 해시면 업로드 생략                                                 | 다른 페이지에 같은 사진을 올려도 DB에는 한 벌                                                                    |
| 페이지 4개 동시 처리                                                    | 다운로드·변환·업로드가 겹친다. Notion API 호출은 위 대기열이 따로 제한한다                                       |
| 요청별 30초 타임아웃, 일시 오류(네트워크·5xx·429)만 최대 3번 재시도     | 만료 링크(403) 같은 영구 오류는 바로 실패해 시간을 낭비하지 않는다                                               |
| 크기 상한 50MB, 받는 도중에도 검사                                      | Content-Length가 없거나 틀려도 메모리를 다 쓰지 않는다                                                           |

외부 링크(Notion에 올리지 않은 이미지)는 같은 주소라도 내용이 바뀔 수 있어 캐시하지 않고, 페이지가 바뀔 때마다 내려받아 해시로 비교한다.

### axios를 쓰지 않은 이유

Node 내장 `fetch`(undici 기반)를 쓴다.

- Node 18부터 `fetch`가 내장되어 있고 Node 26(이 저장소 기준)에서는 안정 기능이다. 2026년 기준 새 Node 프로젝트에서 HTTP 클라이언트 의존성을 따로 두지 않는 쪽이 일반적이다.
- 여기서 하는 일은 Notion API 호출과 사진 내려받기뿐이다. axios의 장점(인터셉터, 브라우저·Node 공용 어댑터, 자동 JSON 변환)이 쓰일 데가 없다.
- 필요한 기능은 내장으로 된다: 타임아웃은 `AbortSignal.timeout()`, 크기 상한은 `response.body` 스트림을 읽으며 검사. 재시도는 어느 쪽이든 직접 짜야 한다(axios도 기본 재시도가 없다).
- Notion SDK도 내부에서 `fetch`를 쓴다. 같은 클라이언트를 쓰면 프록시·TLS 설정이 한 군데로 모인다.
- 의존성이 하나 줄어 공급망 위험과 설치 크기가 줄어든다.

## 예외 처리

원칙: **한 페이지의 실패가 다른 페이지를, 한 DB의 실패가 다른 DB를 막지 않는다.** 실패한 것은 다음 실행에서 저절로 다시 시도되게 하고, 사람이 고쳐야 하는 문제는 고칠 방법과 함께 알린다.

| 상황                                              | 동작                                                                                                       | 다음 실행                                                   | 사람이 할 일                                         |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------- |
| 환경 변수 누락·오타                               | 시작 전에 빠진 이름을 모두 출력, 종료 코드 2                                                               | 같은 오류                                                   | Railway Variables 확인                               |
| Notion 토큰 오류(401)                             | "NOTION_TOKEN이 틀렸거나…" 안내, 종료 코드 2                                                               | 같은 오류                                                   | 토큰 재발급                                          |
| DB를 integration에 공유하지 않음(404)             | 어느 DB인지와 "연결에 integration 추가" 안내, 종료 코드 2                                                  | 같은 오류                                                   | Notion DB → 연결 추가                                |
| Notion 스키마가 표와 다름                         | 아무것도 쓰지 않음. 속성별 차이(대소문자만 다른 이름 포함) 출력, `sync_state.last_error` 기록, 종료 코드 2 | 같은 오류                                                   | Notion 속성 이름·타입을 표에 맞추거나 코드 수정 요청 |
| 429·529 (속도 제한·과부하)                        | `Retry-After`만큼 전체 대기 후 재시도                                                                      | —                                                           | 없음                                                 |
| Notion 5xx·네트워크 일시 오류                     | 지수 대기로 최대 8번 재시도. 그래도 실패하면 그 DB만 실패 처리                                             | 그 DB를 다시 조회                                           | 계속되면 Notion 상태 페이지 확인                     |
| 한 페이지 변환·저장 실패                          | 그 페이지만 건너뛰고 나머지 반영. **그 DB의 커서를 옮기지 않음**                                           | 실패한 페이지를 다시 읽음(나머지는 수정 시각이 같아 건너뜀) | 로그의 페이지 이름 확인                              |
| 이미지 링크 만료(403)                             | 재시도 없이 그 페이지 실패                                                                                 | 새 링크로 다시 받음(조회할 때마다 새 링크가 나옴)           | 없음                                                 |
| 이미지 형식을 읽을 수 없음(HEIC 등)               | "JPG·PNG·WebP·AVIF·GIF로 올려 주세요"                                                                      | 계속 실패                                                   | Notion에 다른 형식으로 다시 올리기                   |
| 이미지가 50MB 초과                                | 받는 도중 끊고 그 페이지 실패                                                                              | 계속 실패                                                   | 사진 크기 줄이기                                     |
| 사진 파일 저장 실패                               | 그 페이지 실패. 1600 파일이 없으니 "미완료"로 남음                                                         | 다시 업로드                                                 | 계속되면 DB 연결·용량 확인                           |
| 조회 결과가 행 수 상한에서 잘림                   | 잘린 목록으로 지우지 않도록 그 DB 실패 처리                                                                | 같은 오류                                                   | (현재 규모에선 일어나지 않음)                        |
| Notion 목록이 통째로 비어 있는데 DB에는 행이 있음 | 삭제를 건너뛰고 경고. 권한이 빠졌을 때 전부 지워 버리는 사고를 막음                                        | 같은 경고                                                   | 정말 비운 거라면 `pnpm sync --full`                  |
| 사진 파일 정리 실패                               | 경고만 남기고 계속                                                                                         | 다시 정리                                                   | 없음                                                 |
| 빌드 알림 파일 쓰기 실패                          | `_dispatch` 상태에 "보류" 기록, 종료 코드 1                                                                | 바뀐 게 없어도 다시 알림                                    | 서버 디스크 확인                                     |

종료 코드: **0** 성공, **1** 일부 실패(나머지는 반영됨, 다음 실행에서 다시 시도), **2** 시작하지 못함(사람이 고쳐야 함). Railway 로그와 배포 기록에서 0이 아닌 실행을 실패로 구분할 수 있다.

## `sync_state`

| `database`                           | 내용                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `members` `awards` `projects` `faqs` | `last_synced_at`(다음 증분 조회 기준), `last_run_at`, `last_result`(개수·소요 시간), `last_error` |
| `_image_cache`                       | Notion 파일 주소 → `image_key`·크기. 지금 쓰이는 이미지만 남긴다                                  |
| `_r2_orphans`                        | 쓰이지 않게 된 `image_key`와 처음 발견한 시각                                                     |
| `_dispatch`                          | `{ "pending": true }`면 빌드 호출이 실패해 다음 실행에서 다시 부른다                              |
| `_running`                           | 지금 실행 중인 동기화(`trigger`: `cron`·`admin`, 시작 시각). 겹침 방지 잠금, 30분 지나면 무효     |

사이트 빌드는 `sync_state`를 읽을 필요가 없다.
